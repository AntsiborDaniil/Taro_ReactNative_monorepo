# BACKUP_POLICY — политика бэкапов

Что бэкапим, как часто, где храним и как восстанавливаем. Связано с [PHILOSOPHY.md](PHILOSOPHY.md) (п. 6, 14) и [CURRENT_STAGE.md](CURRENT_STAGE.md).

## Что важно и где живёт

| Данные | Где | Риск потери | Чем защищено |
|---|---|---|---|
| Прод-БД: профили, расклады, ⚡ и платежи, привычки, настроение, уведомления | Supabase Postgres, ref `urrbsxwlmsfedezwtglm` | Высокий: деньги и история пользователей | Бэкапы Supabase + ручной дамп (ниже) |
| Схема БД | `supabase/migrations/` в git | Низкий | Git + GitHub |
| Код | GitHub, ветка `main` | Средний, пока изменения не запушены | Коммиты и push |
| Секреты (`.env`, ключи OpenAI, Lava, Telegram, Supabase service_role) | Локальные `.env`, переменные Render / Vercel / Timeweb, GitHub Secrets | Средний: в git их нет намеренно | Менеджер паролей владельца |
| Астро-профиль пользователя | `localStorage` браузера (`mt.astroProfile.v1`) | Пользователь теряет при очистке браузера | Не бэкапится — осознанно (приватность). Если профиль поедет на сервер, пересмотреть |
| Кэш гороскопов | Память процесса API | Нулевой: генерируется заново | Не бэкапится |

## Прод-БД (Supabase)

**Автоматически.** Supabase делает ежедневные бэкапы на платных планах; срок хранения зависит от плана, PITR — отдельная опция. Владельцу: проверить в Dashboard → Database → Backups, какой план и сколько дней хранится, и вписать сюда.

**Вручную — обязательно:**

- **Перед каждой миграцией, которая меняет или удаляет данные** (`DROP`, `ALTER ... TYPE`, `UPDATE`/`DELETE` без узкого `WHERE`, пересоздание constraint), и перед ручными правками в проде:
  ```bash
  supabase link --project-ref urrbsxwlmsfedezwtglm
  supabase db dump -f backups/$(date +%F)-schema.sql
  supabase db dump --data-only -f backups/$(date +%F)-data.sql
  ```
  Миграции из `main` выкатываются автоматически (`.github/workflows/supabase-deploy.yml`), поэтому дамп делается **до мержа/пуша** в `main`, а не после.
- **Раз в неделю** — полный дамп (схема + данные), даже если миграций не было.

**Хранение дампов:** вне репозитория и вне ноутбука — зашифрованное облачное хранилище владельца. В дампах персональные данные, поэтому в git их не кладём (папка `backups/` в `.gitignore`). Храним последние 4 недельных и все дампы «перед миграцией» за 3 месяца.

**Проверка восстановления:** раз в месяц поднять дамп на локальном Supabase (`pnpm supabase:start`, затем `psql` с дампом) и убедиться, что данные читаются. Непроверенный бэкап — не бэкап.

## Код

- Незапушенная работа — единственная копия. Конец рабочей сессии → коммит и push (при необходимости в отдельную ветку `wip/...`).
- Перед `git reset --hard`, `git checkout -- .`, `git clean`, `rebase` с крупным незакоммиченным деревом — `git stash push -u -m "<что>"` или WIP-коммит в ветку.
- `apps/native` — отдельный submodule со своим репозиторием, пушится отдельно.

## Секреты

- Все ключи из `.env` и переменных хостингов продублированы в менеджере паролей владельца. Новая переменная → в `.env.example` (без значения), `DEPLOY.md` и менеджер паролей.
- При ротации ключа старое значение не храним.

## Правила для агента (Claude)

1. Не выполнять без явного подтверждения владельца: `supabase db push` / `db reset` против привязанного прод-проекта, SQL с `DROP`/`TRUNCATE`/`DELETE` в проде, `git push --force`, `git reset --hard`, удаление незакоммиченных файлов.
2. Миграция, меняющая или удаляющая данные → в ответе напомнить про ручной дамп перед пушем в `main`.
3. Перед массовыми правками в рабочем дереве с чужими незакоммиченными изменениями — предложить stash или WIP-коммит.
4. Дампы и `.env` никогда не коммитить и не читать без необходимости.

## Восстановление (кратко)

1. Остановить запись: приостановить сервис API на Render (иначе пользователи пишут в битую БД).
2. Восстановить: Dashboard → Database → Backups (автобэкап / PITR) или `psql "$DB_URL" -f <dump>.sql` из ручного дампа.
3. Сверить последние платежи Lava с таблицами ⚡ — платежи после точки восстановления начислить вручную.
4. Запустить API, `pnpm deploy:check-health`, записать инцидент в `docs/`.
